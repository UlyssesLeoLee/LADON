# 10. 总体要件定义（システム要件定義）

## 1. 背景与目标
系统围绕既有已批准要件定义形成“文档即任务”开发工作法，以文件事件为触发源、条款指纹为增量判断依据、.NEMA 作为文档关系及并行任务表示；任何文件管理动作都不能被云端或 AI 响应阻塞。历史数据可冷存储于用户选定的 Google Drive/NAS，本地保存小体量热索引。

## 2. 利益相关者
项目负责人：审核需求/版本；开发者：编辑文件/文档；Agent：在授权 FileSpace 操作；管理员：配置云端、密钥、敏感规则；审计者：查询版本来源。外部角色：Google Drive OAuth，NAS 等 Provider。

## 3. 系统范围
包含原生文件管理、持续历史、文档锚点治理、.NEMA/任务、文件标签和搜索、多 Agent 协同、冷归档及隐私隔离。排除：替代 Windows Explorer Shell 基础桌面进程、默认为所有历史无限上传、访问用户未授权的私人目录、不经批准删除有状态 Worktree。

## 4. 业务流程
1. 指定项目根目录→注册已批准要件基线→扫描创建 FileRef/初始 Hash/版本。
2. 编辑产生文件变动→事件合并→Hash 比较→新增稳定版本与内容 CAS →关联受影响条款。
3. 提交新需求→索引命中批准要件→仅分析有影响的节点→生成文档内联任务→并行 FileSpace 读取/拟定变更。
4. 人审批准→事务/版本检查提交→产生新事件→更新任务与标签→非敏感历史被加密归档。
5. 查阅历史→Turso 查询轻量时间线→按需从云端获取解密的实际版本内容→Diff/恢复。

## 6. 数据相关要求
非敏感历史应长期可查、每版本记录存储状态；原始文件不复制到数据库；CAS 只保存必要快照；云盘可迁移，Provider ID 不作为逻辑文件身份；Turso 仅存热索引，其他历史事件可以按段归档。

## 7. 一致性与时点
首次基线之前的未知历史不得伪造；通知事件并不意味着文件已稳定保存；版本以被系统捕获并完成事务提交为准。外部修改造成的分叉必须人工解决或作为独立来源标记。

## 8. 变更控制
批准 REQ 的 ID 永久稳定；变更引入 CR 和版本，不直接覆盖已有基线。每个 CR 应记录需求来源、5W1H、影响条款、多个建议选项、选择依据和审批人。
