# 11. 文档即任务 / 要件锚点治理业务要件

## 1. 假定的既有文档
接入时项目已存在**已批准的要件定义**，它不是由 AI 在初始化时重建的。导入后按文件、章节、条款建立稳定锚点；如果找不到批准状态或缺失对应文档，则提示需要用户指定，不能默认 AI 自造要求。

## 2. 文档即任务实体
`DocumentAnchor = (FileRef, section_key, base_version_id, approval_id)`；`Annotation = (anchor, text, author, rationale, visibility)`；`Task = (anchor, title, description, owner, status, dependency_ids, approval)`；`ChangeProposal = (base_version, diff, impact, risk, chosen_option)`。

## 3. Task 状态
`open → analysis → approval → working → verification → done`，可从等待阶段到 `cancelled`；状态变化必须产生治理事件，不能只修改 UI 本地状态。

## 4. 新需求增量对照
Hook 捕获自然语言需求→在本地已有 REQ 倒排/向量索引筛候选→对相关已批准条款取内容指纹与简述→检测一致、冲突、待澄清及影响→仅把少量相关条款送给模型→返回 `CR-xxx + file_ref + section_key + recommended_choices + severity`。普通文件修改无需每次全量 AI，Hash 不变则直接跳过。

## 5. 内联审批
用户在文档光标或选中段落处打开内联批注；Agent 提供差异和原因，不允许直接更改已批准要件原本版本；提交新版本后旧注释仍指向旧基线，必要时执行锚点迁移报告。

## 6. 版本语义
同一 FileRef 的重命名、移动不应丢失注释和任务；移动到云端冷存储时仍能按历史版本查看。外部不确定同一性（例如复制+删除）不得静默合并历史。

## 7. 与 .NEMA 的联系
Table：版本/标签/任务状态；5W1H：变更的 what→why→how→who→when→where；Node–Edge：REQ→DES→DETAIL→CODE→UT/IT/ST、任务 DAG。节点必须有稳定 ID，边变化应独立审计。

## 8. 完成判定
用户新增一个要件注释后，可以从同一位置查看所有下游任务、Agent 变更、提交事件、测试证据及回滚链；结果可导出 .NEMA 关系和审计报告。
