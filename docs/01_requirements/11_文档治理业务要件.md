# 11. 文档即任务 / 要件锚点治理业务要件

## 1. 假定的既有文档
接入时项目已存在**已批准的要件定义**，它不是由 AI 在初始化时重建的。导入后按文件、章节、条款建立稳定锚点；如果找不到批准状态或缺失对应文档，则提示需要用户指定，不能默认 AI 自造要求。

## 2. 文档即任务实体
`DocumentAnchor = (FileRef, section_key, base_version_id, approval_id)`；`Annotation = (anchor, text, author, rationale, visibility)`；`Task = (anchor, title, description, owner, status, dependency_ids, approval)`；`ChangeProposal = (base_version, diff, impact, risk, chosen_option)`。

## 3. Task 状态
`open → analysis → approval → working → verification → done`，可从等待阶段到 `cancelled`；状态变化必须产生治理事件，不能只修改 UI 本地状态。

## 4. 新需求增量对照
Hook 捕获自然语言需求→在本地已有 REQ 倒排/向量索引筛候选→对相关已批准条款取内容指纹与简述→检测一致、冲突、待澄清及影响→仅把少量相关条款送给模型→返回 `CR-xxx + file_ref + section_key + recommended_choices + severity`。普通文件修改无需每次全量 AI，Hash 不变则直接跳过。

## 5. 内联审批
用户在文档光标或选中段落处打开内联批注；Agent 提供差异和原因，不允许直接更改已批准要件原本版本；提交新版本后旧注释仍指向旧基线，必要时执行锚点迁移报告。

## 6. 版本语义
同一 FileRef 的重命名、移动不应丢失注释和任务；移动到云端冷存储时仍能按历史版本查看。外部不确定同一性（例如复制+删除）不得静默合并历史。

## 7. 与 .NEMA 的联系
Table：版本/标签/任务状态；5W1H：变更的 what→why→how→who→when→where；Node–Edge：REQ→DES→DETAIL→CODE→UT/IT/ST、任务 DAG。节点必须有稳定 ID，边变化应独立审计。

## 8. 完成判定
用户新增一个要件注释后，可以从同一位置查看所有下游任务、Agent 变更、提交事件、测试证据及回滚链；结果可导出 .NEMA 关系和审计报告。

### 9.3 终态迁移表（T1～T11）

所有迁移在一个 Immediate 事务内完成：读取当前状态、检查迁移表与守卫、以 `UPDATE … WHERE id=? AND status=旧` 更新且要求影响 1 行、写入附带行、追加链事件。表中未列出的迁移返回 `E_TRANSITION_DENIED`，错误信息列出调用者当前可做的迁移。执行者：H 为人（需人在场证明），A 为 Agent（MCP，固定主体），S 为系统（对已验证事实的反应）。

| 编号 | 迁移 | 执行者 | 守卫 | 附带写入 | 事件 |
|---|---|---|---|---|---|
| T1 | open → analysis | H、A | `proposal_state=accepted`；锚点状态不是 `orphaned`、`file_missing`、`ambiguous` | — | `dt.task.transitioned` |
| T2 | analysis → approval | H、A，仅随方案提交 | 同一事务内提交方案（可为只分析方案）；方案字段合法；编辑方案另须通过 `EditPlanSupport` 校验（第 8.1 节），未注册该组件时只接受只分析方案 | 方案行（`submitted`），旧的 `submitted` 方案变 `superseded` | `dt.plan.submitted`、`dt.task.transitioned` |

| T6 | verification → done | **H** | 见 4.5 | 批准行（`result`/`approved`）；`closed_at` | `dt.approval.recorded`、`dt.task.transitioned` |

| T10 | done、cancelled → open | **H** | 理由必填 | 清 `closed_at` | `dt.task.reopened` |
| T11 | approval → analysis（方案过期） | **S** | 仅在 T3 守卫 4 判定方案过期时，与方案 `superseded` 同一事务 | 方案 `superseded` | `dt.plan.superseded`、`dt.task.transitioned`（`actor_kind=system`，原因 `stale_plan`） |

状态沿用 7 个字符串：`open`、`analysis`、`approval`、`working`、`verification`、`done`、`cancelled`。`done` 与 `cancelled` 是终态，只有 T10 能离开。提案（`proposal_state=proposed`）在人工采纳（P1）之前不能离开 `open`。

### 9.4 人工专属操作

Agent 可调用的迁移只有 T1、T2（随方案提交）、T5、T7（最新证据为失败时）与 T8。T11 只由系统在 T3 守卫 4 判定方案过期时执行。其余迁移全部是人工专属。以下操作同样是人工专属，服务层对 Agent 与 System 返回 `E_HUMAN_ONLY`：

- 基线登记与撤销；
- 批准（T3）、驳回（T4）、验收（T6）、取消（T9）、重开（T10）与人工执行的 T7；
- 采纳（P1）与忽略（P2）提案；
- 方案应用（`doc apply`）与恢复决定（`doc recover`）；
- 任务属性（负责人、优先级、可见性）编辑；批注公开与取消公开；
- 锚点确认（`ack`）、重定位（`relocate`）与重定基（`rebase`）；
- 谱系确认与拒绝；导出报告到文件。

人工专属操作的服务签名都带展示时的 `expected_*`。确认方式如下，任何非精确输入都视为放弃，不产生写入：

| 操作 | 确认方式 |
|---|---|
| 批准、应用、验收 | 展示将作用的内容与绑定哈希，要求键入任务号（如 `T-12`）；不能由 `--yes` 跳过 |
| 驳回、取消、重开、忽略 | 理由必填（非空），再以 `y/N` 确认 |
| 登记与撤销基线、采纳提案、确认锚点、重定位、重定基、谱系确认 | 展示对象（含版本号与内容哈希前 8 位）后以 `y/N` 确认。`--yes` 只在同时给出 `--expect-hash`（至少 8 位十六进制前缀）时有效，否则 `E_INVALID_ARG`；它仍要求真实控制台 |

基线登记、`ack` 与 `rebase` 还要比较现存文件摘要与账本的当前哈希，不符则返回 `E_FILE_CHANGED`，使所有者批准的永远是账本中已有的版本。

### 9.5 治理事件链

链是工作区内一条 `doc_task_events` 序列。每个事件的 `hash` 为下列元组经 `serde_json::to_vec` 序列化后的 SHA-256，创世 `prev_hash` 为 64 个 `0`，`payload_json` 以存储的文本原样参与，不重新序列化：

`(prev_hash, id, task_id, file_id, subject_kind, subject_id, kind, from_status, to_status, actor, actor_kind, session, claimed_session, payload_json, timestamp)`

- 元组一经发布即冻结，由金标测试锁定。
- 链尾在追加所在的同一 Immediate 事务内读取；`prev_hash` 上的唯一索引使承接同一链尾的后一个插入失败，写入方重读链尾并重试，至多 3 次。
- `session` 是权威会话（`hermes:<launch_id>`）；`claimed_session` 是模型自称的会话 id，只记录，不信任。
- 批注事件的载荷只含批注文本的 SHA-256 与长度；任务事件的标题同样只记哈希与长度。
- 链是无签名的防篡改证据。对整库的重写无法阻止，由 `doc verify` 的回放检出的是事件级的篡改、删除与不合法迁移。

### 9.6 基线与锚点规则

- 同一 `(file_id, version_id)` 同时至多一条未撤销的基线（`BASELINE_DUPLICATE`）。撤销后同一版本可重新登记，载荷带 `replaces_revoked`。
- 锚点状态为 `valid`、`needs_review`、`relocated`、`unknown`、`orphaned`、`ambiguous`、`file_missing`。T3 与 T6 只接受 `valid`，以及经 `ack` 或 `relocate` 确认的 `needs_review`、`relocated`、`unknown`。`orphaned`、`ambiguous`、`file_missing` 一律拒绝。
- 条款以标题键与正文哈希识别。改名且正文相同为 `relocated`；正文改动为 `needs_review`；多个相同正文为 `ambiguous`；前置重复标题为 `relocated`（`full_hash`）；正文过短不自动重定位。对账不静默重定基。
