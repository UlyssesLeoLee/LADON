# 31. 事件驱动版本管理详细设计

## 1. 输入输出
输入 `FileEvent{path,kind,observed_at,origin}` 或手工 `capture(path, actor, reason)`；输出 `CaptureResult{file_ref,version_id,event_id,changed_sections,sensitivity}`。监听事件**只作通知**，不直接当作文件内容的事实。

## 2. 稳定保存算法
1. `notify` 观察到事件，按路径防抖（目前 350ms）；未来追加大小/mtime 双稳定检查、USN 增量游标。
2. 通过 `canonicalize` 验证工作区内及符号链接风险；普通文件以 64KiB 流式读取、SHA-256、Zstd 写 CAS 暂存。
3. 对比读取前后 size/mtime；变化时拒绝本次捕获，等待下个事件。
4. `current_hash` 未变化则返回 `unchanged`，不新增版本。
5. 新版本读取前版/后版小于限制时按 Markdown Headings 或 .NEMA Domain 对比；巨型文本/二进制只标记待细分。
6. Turso 事务：更新 resource 当前 Hash/版本号→INSERT version→INSERT chained event→COMMIT。
7. 由版本事件产生标签失效和受影响要件筛选任务（详细功能后续）。

## 3. 事件哈希链
`event_hash = SHA256(serialize(prev_chain_hash, event_id, file_id, version_id, kind, old_path, new_path, timestamp, actor, reason, previous_content_hash, current_content_hash))`，以 FileRef 为分链。为提升法证可信度，生产版还需链头签名与外部不可变检查点；未签名 Hash 链不能防止攻击者重写整个库。

## 4. 恢复算法
指定版本→验证文件存在、版本关联和授权→读取本地 CAS 或已验证 Provider→解密及 SHA-256→检查当前文件是否与记录 Hash 一致→产生 Dry-run→人工批准→写临时文件→OS 替换→作为新版本重新捕获。Windows 覆盖语义与失败回滚仍需增强（已在风险表标注）。

## 5. 状态机
版本状态 `CURRENT`, `HISTORIC`, `TOMBSTONED`; 归档状态 `LOCAL`, `QUEUED`, `UPLOADING`, `REMOTE_WRITTEN`, `VERIFIED`, `EVICTABLE`, `COLD`, `CORRUPT`。本期 DB 保存经过验证的 ArchiveObject，并非完整持久队列。

## 6. 对抗场景
- 文件在 Hash 读取中继续写入→mtime/size 前后不同，拒绝。
- 同一内容多次保存→只保留一次版本。
- 存储访问中断→归档失败，CAS 保留。
- 先发生事件、后发生路径变化→核对 File ID 或补扫，绝不错误复用旧内容。
- 文件删除→Turso 资源标记 deleted；历史对象不删除。
- 日志断档→明确审计间隙，重新扫描基线，不能伪造中间版本。
