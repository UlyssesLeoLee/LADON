# 34. .LADONignore 安全策略详细设计

## 1. 命名与规则
用户约定文件名为 `.LADONignore`（大小写严格遵守项目规范）；界面文字“LADON Ignore”。解析采用 `ignore::gitignore::GitignoreBuilder` 风格，支持 `*`, `**`, 目录、`!` 例外、`#` 注释。加载顺序为全局规则文件、根规则文件、嵌套规则文件，后加载的规则优先于先加载的规则。全局规则文件为 `LADON_GLOBAL_IGNORE` 指定的文件。变量已设置（包括设为空值）时，其值必须指向可读取的文件；指向不存在或不可读取的文件、或空值时，加载、`LadonPolicy::check_root` 与打开均失败（失败关闭）。变量未设置时不加入全局规则。根规则文件为工作区根目录直接子项中名称与 `.LADONignore` 在 ASCII 大小写不敏感比较下相同（包括完全一致）的普通文件，指向普通文件的符号链接同样生效（所有平台）。嵌套规则文件为深度不小于 2 的普通文件（根目录深度为 0，即任一子目录中的文件），名称必须与 `.LADONignore` 完全一致（区分大小写）；符号链接形式的嵌套规则文件被跳过。嵌套规则文件解析前去除开头的 UTF-8 BOM（`add_nested_rule_file`）。遍历不跟随链接，不进入 `.ladon` 与 `.git` 目录。打开与初始化时同步检查全局规则文件与根目录的 `.LADONignore`（`LadonPolicy::check_root`），全局规则文件或根目录的 `.LADONignore` 任一无法解析时，打开或初始化失败；工作区根目录不存在名称与 `.LADONignore` 在 ASCII 大小写不敏感比较下相同的普通文件时（报告 `root rule file .LADONignore is missing`），打开失败。全量扫描在后台线程进行（`PendingPolicy`），打开与初始化不等待扫描结束。记录（`capture`、`scan`）与外部归档（`archive_version`）等需要判断排除的操作等待当前扫描结束；扫描中任一规则文件无法解析，或目录遍历出错（错误文本以 `failed to scan the workspace:` 开头）时，这些操作返回该错误，不记录也不上传，不静默丢弃规则；`PendingPolicy` 此后每次使用都返回同一错误。`restore` 经由 `capture` 记录；记录失败时，目标文件仍为恢复出的字节则回滚为调用前的文件（替换前不存在原文件时移除目标文件），否则保留目标文件（替换前存在原文件时同时保留其备份），并在错误中给出路径（详见 `36_数据库事务与变更策略.md` 第 3 节）。恢复文件放置时不替换目标路径上的既有文件。`reload_policy` 同步检查全局规则文件与根目录的 `.LADONignore`。检查失败时外部归档被阻止，直到后续重载成功，并返回错误。根目录的 `.LADONignore` 缺失时，规则集同时替换为失败状态，此后记录（`capture`）也返回 `root rule file .LADONignore is missing`，直到后续重载成功；其他检查失败时规则集保持调用前的状态。检查成功时启动新的全量扫描，替换当前规则集，不等待扫描结束。监视命令（`ladon watch`，`src/main.rs` 的 `watch`）逐个处理文件事件路径：路径含 `.ladon` 或 `.git` 组件时忽略；父目录为工作区根且文件名与 `.LADONignore` 在 ASCII 大小写不敏感比较下相同的路径（`policy::is_root_rule_event`），以及任一目录下文件名与 `.LADONignore` 完全一致（区分大小写）的路径，调用 `reload_policy` 且不记录该路径，也不触发全量扫描。其余路径逐个处理：普通文件经 `capture` 记录；其他路径（目录，或已不存在的路径）若在账本中有相同相对路径的被跟踪文件，则标记删除。批次中任一路径满足 `policy::needs_full_scan`（非普通文件，且不是根规则文件）时，该批次处理结束后对工作区执行一次全量扫描（`Engine::scan`），由扫描记录新路径并标记不再存在的被跟踪路径；因此含删除或目录事件的批次会执行一次完整遍历。`watch` 不调用 `need_rescan`，Windows 事件缓冲区溢出时丢失的变更不会被自动对账，需手动执行 `scan`（已知限制）。名称大小写不同的嵌套规则文件不触发重载，按普通文件记录。重载失败时输出错误，外部归档按 `reload_policy` 的规则被阻止。工作区目录不存在时加载失败，错误文本为 `workspace not found`。所有规则合并为以工作区根为基准的同一个匹配器。非否定模式按根相对解释，因此无论来自哪个规则文件都作用于整个工作区（嵌套规则文件中的非否定模式不按目录限定，已知限制）；以 `/` 开头或含中间 `/` 的模式从根锚定而非从其所在目录锚定（已知限制），其余模式在任意深度匹配。嵌套规则文件中的否定模式（`!`）只作用于该文件所在目录之下：不含中间 `/`（末尾 `/` 不计）的模式改写为 `!<目录>/**/<模式>`，以 `/` 开头或含中间 `/` 的模式改写为 `!<目录>/<模式>`，目录名按 glob 规则转义；根规则文件与全局规则文件中的否定模式不改写。Windows 下全部规则（含全局、根与嵌套规则文件）按 ASCII 大小写不敏感匹配（`rule_builder`），其他平台区分大小写。工作区内不存在任何规则文件（根目录的规则文件按名称大小写不敏感查找，嵌套规则文件按精确名称查找），且未设置 `LADON_GLOBAL_IGNORE` 时，规则集为空，`LadonPolicy::load` 仍成功返回。`LadonPolicy::load` 不检查根规则文件；`Engine::open` 与 `reload_policy` 经 `LadonPolicy::check_root` 检查，因此根规则文件缺失时两者拒绝（见上文）。`AgentApi::allow_remote_read` 与 `tag-folder` 直接调用 `LadonPolicy::load`，`ladon ignore-check` 同样如此；引擎打开后根规则文件被删除而未调用 `reload_policy` 时，这些入口以空的根规则集判定（已知限制）。`Engine::init` 在工作区根目录不存在 `.LADONignore` 文件时（`src/engine.rs` 中的 `if !rule.exists()`）写入示例规则文件，`Engine::open` 不写入。

`add_sensitive`（右键“添加为敏感文件”与 `ladon sensitive-add`）向根 `.LADONignore` 追加以 `/` 起始的根锚定规则：路径分隔符（含 `\`，所有平台）先统一规范化为 `/`，再将路径中的 `* ? [ ] { } ! # \` 以反斜杠转义，目录规则以 `/` 结尾，同一规则不重复写入，并写入注释行 `# LADON sensitive: exclude remote transfers`。在非 Windows 平台上，名称中的 `\` 被改写为 `/`，名称末尾的空格未被转义，名称中的换行未被拒绝，写入的规则可能与该文件不匹配（已知限制）。目标必须已存在；工作区根目录本身、`.ladon/` 下内容和根目录的 `.LADONignore`（精确名称）不可作为目标（返回 `invalid ignore target`），目标位于工作区之外时返回 `cannot exclude resource outside workspace`；规则只约束此后的外传，不撤回已上传的数据。

## 2. 命中语义
`.gitignore` 仅控制 Git 追踪，本规则控制**外部数据流**。匹配文件仍可本地查询、建立历史、编辑/恢复，默认禁止 Google Drive/NAS 外存外传，以及排除文件发往非本机端点的 AI 请求（外存归档由 `Engine::archive_version` 拦截，AI 标签由 `src/main.rs` 判定，判定规则见 `36_数据库事务与变更策略.md` 第 5 节；Agent 远程读取入口 `AgentApi::allow_remote_read`（异步）同样按路径规则拦截，并以账本中被跟踪文件的当前内容哈希判定排除内容；磁盘上已改写为排除内容但尚未被捕获的文件，以及未在账本中记录的副本路径，不被检测（已知限制））。远端 Embedding 与日志同步的外传禁止属于设计要求：当前代码无 Embedding 外传路径，日志同步的 `cloud_journal::publish_segment` 带敏感门控但无运行路径调用方（仅单元测试调用）。`.LADONignore` 本身、`.ladon` 应用目录及 `.git` 内部数据强制保护，不接受 `!` 例外覆盖；这些路径无需任何规则即判定为排除。内部目录判定作用于完整路径（包括工作区根之上的祖先目录）：工作区位于名为 `.git` 或 `.ladon` 的目录之下时，记录与扫描报告失败，`tag-folder`、`watch` 与 `grep` 静默忽略全部路径（已知限制）。`excluded` 以精确名称（区分大小写）判定规则文件自身，任意深度的 `.LADONignore` 均排除。名称大小写不同的根规则文件（如 `.ladonignore`）虽被加载为规则，却不在此强制排除，扫描也只跳过精确名称的根文件，因此它可被扫描记录且不受强制保护（已知限制）。

`excluded` 对相对路径按工作区根解析；绝对路径必须位于工作区的规范化根之下（Windows 下为 `\\?\` 扩展长度形式），否则返回 `outside workspace` 错误。`excluded` 不规范化 `..` 组件，根前缀检查按路径组件做词法比较：相对路径拼接工作区根后检查，绝对路径原样检查。因此含 `..` 组件的路径，无论是相对路径还是位于工作区根之下的绝对路径，都不返回 `outside workspace`，`allow_external` 也不因其越出工作区而拒绝（已知限制）。`ladon ignore-check` 把参数原样交给 `excluded`、不先规范化：相对路径按工作区根解析；绝对路径须以规范化后的工作区根为前缀（Windows 下为 `\\?\` 形式），普通的 Windows 绝对路径因此返回 `outside workspace`，在 Windows 上应传相对路径（已知限制）。原样传入以大小写不同的 `.LADON` 等内部目录名起始的路径时，`excluded` 不将其视为内部目录（已知限制）。`allow_external` 在路径被排除时返回 `LADON policy denies external data transfer: <路径>` 错误。

## 3. 多级优先级
强制保护集合（内部 DB/证书/密钥） > 全局管理员拒绝 > 工作区拒绝 > 子目录拒绝 > 用户明确的分类例外。生产版要求“某个子目录 `!` 例外不能取消更高层强制保护”，不得简单套用 Gitignore 后返回允许；当前代码实现的是 gitignore 匹配与内部目录强制排除，不包含管理员规则优先级升级。具体而言，同一路径上后加入匹配器的规则优先；路径自身命中的 `!` 例外先于父目录的排除规则判定，因此被排除目录中的文件可以被 `!` 例外重新包含，与 Git 行为不同（Git 不允许重新包含已排除目录中的文件）。嵌套规则文件中的 `!` 例外可以重新包含位于该文件目录之下、被根规则文件的 `add_sensitive` 规则排除的路径：例如 `docs/.LADONignore` 中的 `!secret.md` 使 `docs/secret.md` 重新可外传，即使根 `.LADONignore` 含 `/docs/secret.md`。上文的优先级要求（工作区拒绝高于子目录例外）未被当前实现满足，这是待负责人确认的开放设计问题。

## 4. 重评估与净化
规则发生变化后扫描已归档记录，发现过去泄露敏感资源时生成 `security.reclassification` 事件，显示供应商删除范围并由用户审批远端删除。不能保证平台内部备份立即物理擦除；应提示可见可控的最终状态。当前实现不做重评估与 `security.reclassification` 事件，上述为设计要求。

## 5. 路径安全
先 OS 级 File ID/重解析点检查，之后 Canonical Path 作用域对照，杜绝 `..`、symlink、UNC/device 路径绕过。当前实现未检查 File ID 与祖先目录的重解析点（祖先组件由 `canonicalize` 解析后按根前缀比较，不作拒绝）；路径本身为符号链接时拒绝，规范化后非普通文件时拒绝（`archive.rs` 的 `assert_under_workspace`）。`LadonPolicy::excluded` 先做词法根前缀检查（不规范化 `..`，含 `..` 组件的相对路径或位于根之下的绝对路径可通过该检查，已知限制），再检查 `.ladon`/`.git` 组件与 `.LADONignore` 文件名，随后按 gitignore 规则匹配，并以 `path.is_dir()` 探测目录状态；不做 File ID 或重解析点检查；未来针对 Windows Reparse Point 与大小写不敏感路径逐项 ST。“检查时一个路径、记录时另一个路径”的 TOCTOU 当前未被避免（已知限制）：`capture` 对解析后的路径做策略检查，随后由 `CasStore::put_file` 按路径名重新打开该文件；检查之后该路径被替换为指向工作区之外文件的符号链接时，外部内容会以工作区内的路径被记录。`src/workspace.rs` 的 `FileRef` 只记录标识、路径、版本与内容哈希，不持有已打开的文件句柄。
