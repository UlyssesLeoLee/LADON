# 36. Turso Schema、事务与迁移詳細設計

## 1. Schema 权威来源
`sql/001_initial.sql`；严禁不经 Migration 修改已有用户 DB。版本库增加 `schema_migrations(version,checksum,applied_at)` 并为每次升级提供升级脚本与回滚路径（未来实施）。

## 2. 数据完整性约束
`resources.relative_path` 唯一；`versions(file_id,number)` 唯一，`events.id` 唯一，`archive_objects(content_hash,provider)` 唯一；所有关联 ID 必须经过存在性校验。外键开启与否需在 Turso 实机验证（`PRAGMA foreign_keys=ON`）。

## 3. 事务边界
新增版本 = 一次 DB Transaction，包含 `resources`、`versions`、`events`。CAS 写入先于事务，出现失败时存在可 GC 孤儿。事件账本不可回写旧历史，更新 `resources.current_hash` 只表达当前状态。`restore` 始终创建新版本。

## 4. 索引规划
查询热路径：`FileRef → latest version`、`FileRef → ordered events`、`content_hash → archive objects`、`Tag → matching file ids`、`REQ anchor → edges`。后期按文件/时间分段，旧事件 Detail 进入云端，Turso 保留稀疏索引与定位游标。

## 5. Cloud Sync 不变量
初版 Local-only。后续同步时敏感路径与内容衍生字段不能自动远程复制，需要分库或分类字段加密，并根据敏感策略过滤；即使内容加密仍需评估路径名、访问模式和流量特征泄漏。

## 6. 备份一致性
备份 DB 不得直接复制一个正在写入的 SQLite/Turso 文件（可能遗漏 WAL）；生产版应采用 Turso 支持的一致性备份/Checkpoint API 或独立导出事务方案，获得完整性校验后才上传。

## 7. 查询安全与稳定性
全部入参绑定，不允许 SQL 拼接；查询按 limit/cursor 限制，避免打开 100 万个事件时将历史对象一次性载入内存。`Store` 当前的 `history` 命令未分页；生产版必须加入 cursor 分页并按需从远端懒加载 Diff。
