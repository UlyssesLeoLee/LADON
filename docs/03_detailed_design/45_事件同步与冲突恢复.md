# 45. 詳細設計 — 增量同步、跨设备冲突与缺口恢复

## 1. 多设备日志

每一个 Device Stream 维护 `(tenant,workspace,device,first_seq,last_seq,prev_segment_hash,segment_hash)`。同一设备只允许连续序列；不可变 segment ID = payload SHA256，重试根据 digest 去重。设备间不依赖时钟排序保证一致性。

## 2. 冲突判定

| 场景 | 处理 |
|---|---|
| 不同 FileRef | 可并行应用元数据 |
| 同一 FileRef、不同独立基线 | 比较版本图，必要时三方合并 |
| 同一 FileRef、同一基线、两次不同修改 | 创建 `sync_merge_conflicts`，待审核，不覆盖 |
| 同设备 seq 相交 | 标记数据损坏/重放异常，冻结该设备流 |
| 事件段前驱丢失 | 标注历史不完整，自动从上一个 checkpoint / 其他副本补齐 |
| 被撤销的设备发来新段 | 拒绝团队同步、登记安全审计 |

不要直接将全部本地 Turso 元数据库复制到共享云实例，因为其中可能包含敏感路径、私人标签及本地未授权设备信息。

## 3. 持久化 Outbox

数据库事件事务与文件 CAS 写入采取可恢复状态机。`pending -> uploading -> uploaded -> verified -> indexed -> evictable`。遇磁盘满优先暂停新归档/清理并常显告警；必须保留历史正确性，不可默默丢弃。

## 4. 合并状态的真实界限

`src/cloud_journal.rs::reconcile` 当前仅做同基线/设备序号启发式检测；尚不是真正的分布式合并引擎，也没有跨设备持久锁与故障补偿。
