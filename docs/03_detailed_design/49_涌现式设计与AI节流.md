# 49. 詳細設計 — 事件融合驱动的涌现式能力

## 1. 事件信号

- 文件变更指纹（内容变化实际存在）
- 关系图：受影响的需求/设计/代码/测试 Node–Edge
- 测试结果：回归失败、覆盖率下降
- Agent/团队批注与风险提示
- 版本恢复、归档失败和待审批项

## 2. 合并与门槛

相同根事件的重复通知先按 event_id 去重；按要件锚点聚合，至少 2 类独立来源、置信≥0.6、非敏感。优先由本地规则产生简短“影响范围+证据+处理选项”，需要语义歧义时才用模型，设 Token、时间与频率预算。

## 3. 保护

禁止建议器直接写文件或提交 Agent 结果。用户批准后创建真正 DocumentTask，任务 ID+基线版本写入审计；FileSpace 后续使用 CAS/版本锁提交。人工否决要作为负反馈降低重复建议。

## 4. 示例

用户改 `REQ-023` → 指纹变化；关联的 `TEST-017` 失败 → 两类证据 → 建议检查基本设计与 UT。没有第二类证据时保持安静，避免增加认知负荷。`src/emergence.rs` 提供一个不调用大模型的确定性建议器，尚未具备真实 UI/Task 提交。
