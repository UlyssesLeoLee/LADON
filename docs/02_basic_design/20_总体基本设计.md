# 20. システム基本設計書 — 总体基本设计

## 1. 系统目标与外部边界
LADON Explorer 以“文件即资源、文档即任务、事件即审计”为业务模型。原生 Rust GUI 与 File Runtime 先行启动；AI、OCR、向量、云存储和 LSP 作为按需 Worker，不得阻塞 UI。Windows 原生文件系统是事实来源，Turso 是轻量事件/关系目录，Git/CAS 是内容版本容器，Google Drive/NAS 是冷存储而非实时数据库。

## 2. 分层架构
| 层 | 模块 | 职责 | 依赖约束 |
|---|---|---|---|
| L1 Presentation | Slint GUI | 文件树/历史/注释/操作计划、用户审批 | 只通过 Command Bus 调用服务 |
| L2 Application | Command Bus + UseCase | 业务操作、权限审批、优先级、取消 | 不读写云盘 API 细节 |
| L3 Resource | File Runtime / FileRef | 跨卷路径、文件身份、目录枚举、监控 | 本地使用，不依赖 AI |
| L4 Governance | Event Ledger / Concept Guard | 事件、版本链、条款指纹、要件锚点、任务 | 变更事件驱动，增量筛选 |
| L5 Agent | FileSpace/Plan/Commit | 隔离会话、Snapshot/Delta、DAG、审批 | 独立进程，受权限策略约束 |
| L6 Data | Turso / CAS / Git / Search | 热元数据、版本对象、检索、标签 | 禁止将数据库文件放网络盘 |
| L7 Adapters | Google Drive/NAS/Ollama/MCP/WASM | 存储和 AI 工具插件 | 使用能力协商，不绕过 LADON Guard |

## 3. 正常业务时序
1. 用户打开目录，GUI 立即提交目录枚举任务至 IO Worker，展示部分结果。
2. 文件事件监听通知路径；合并稳定保存事件（避免每次 write 产生重复历史）。
3. FileRef + fingerprint 识别真正变化，Turso 新增版本/event，CAS 中存新增内容对象。
4. .NEMA Node–Edge 查询影响节点，若是非语义修改则跳过 LLM；若需语义分析则选少量条款。
5. AI/人类的修改提案进入审批面板；统一 Commit Coordinator 在写入前检查哈希版本。
6. 经敏感规则判断后，异步上传历史到 Provider；可验证后仅释放本地冷对象。

## 4. 数据一致性与生命周期
- 原文件：永远由原生文件系统管理；不得将影子副本视为“原文件”。
- 文件身份：FileRef UUID 是应用逻辑主键；未来与 Win32 File ID/Volume ID 联合验证，路径不是唯一主键。
- 版本：不可变，`(file_ref, version_no, content_hash, snapshot_ref, timestamp)`。
- 事件：append-only，包含受审计 actor、reason、任务 ID、上个事件 Hash；不以可清除的普通 debug log 替代事件账本。
- 历史内容：CAS 不可变；首次版本需完整快照。今后可以使用 deltas+周期快照，但链长必须有上限。
- 云备份：Provider 数据与逻辑版本独立、可重新放置；冷对象引用需带存储可用性状态。

## 5. 设计制约
- Local-first 与安全优先，不把 Google Drive 挂载盘当 Turso DB。
- `.LADONignore` 是跨模块外传守卫，匹配后的本地审计仍允许。
- 单 EXE 是发行包装目标；运行时允许多 Worker 线程/子进程。
- `FileSpace` 隔离读视图不代表写隔离；写操作必须协调。
- 本期 Rust 实现覆盖内核和 Slint 示例，完整文件管理 GUI 及 Agent Runtime 尚处设计阶段。
