# 00. 开发文档适用范围与 IPA 工程对应

## 0.1 适用范围
产品为面向 Windows 11 的本地优先文件管理及文档治理工具，使用 Rust 原生内核和 Turso；Google Drive 为第一期远端历史存储，NAS/S3 等遵守相同接口，`.LADONignore` 决定敏感资源外传边界。

## 0.2 工程过程映射
| 本交付工程 | IPA 共通フレーム/通常称谓 | 主要成果物 | 管理重点 |
|---|---|---|---|
| 企划/業務要件 | 企画・要件定義プロセス | 业务目标、范围、制约、业务流程 | 既有批准的要件定义被视为锚点 |
| システム要件定義 | システム要件定義プロセス | 功能/非功能要件、受入条件 | 系统边界和责任 |
| 基本設計（外部設計） | システム設計 / ソフトウェア要件 | 系统构成、画面、数据及 API | 面向外部可观察行为 |
| 詳細設計（内部設計） | ソフトウェア詳細設計 | Rust 模块、DB 事务、接口、异常 | 可直接实施的算法/数据结构 |
| 実装・UT | ソフトウェア構築 / 単体テスト | Rust 代码、单元测试 | 功能单元正确性 |
| IT（結合テスト） | ソフトウェア結合/結合テスト | API/DB/Archive 协作验证 | 模块间边界 |
| ST（総合テスト） | システム適格性確認テスト | 端到端/非功能/故障注入 | 需求被满足 |
| UAT（受入テスト） | システム受入れ支援 | 用户场景、签收与缺陷清单 | 用户自主批准 |

**说明：** IPA 共通フレーム2013 不规定固定的官方标准文档模板，具体成果物按项目裁剪。本包按实施需求自编，不声称 IPA 认证。

## 0.3 证据链
每项 REQ → 基本设计 → 详细设计 → 代码路径 → UT/IT/ST Case → 执行证据 → 合格判定。任何 `Design` / `Partial` 的功能不能因测试案例存在而判为交付完成。

## 0.4 质量门禁
G1 要件基线获得正式批准；G2 设计关键风险与接口评审通过；G3 Rust 构建、Clippy、UT 通过；G4 IT 通过且无严重缺陷；G5 ST 性能、安全、恢复实测通过；G6 用户验收与部署签字。

## 0.5 审核与变更
批准的 REQ 条款内容、版本和批准人必须可追溯。新需求进入时只触发相关文档的增量对照；新增/删除条款需形成变更请求 CR-xxx 及影响分析，不允许静默覆盖批准基线。
