# Technical Design: `src/engine.rs`

Source: `src/engine.rs`

Source-SHA256: `bb181e0f9d22e3fdc818b2c9d50ab5c07ccbcf3ce5fd5b967d44e7f8aad8323f`

## Responsibility

`Engine` is the orchestration layer for one workspace root. It combines the metadata `Store`, the content-addressed `CasStore` under `.ladon/cas`, and the `.LADONignore` policy. It turns file-system observations into ledger events: capturing a file as a new version, scanning a whole tree (including detecting deletions), archiving a version to an external provider as an encrypted object, loading historical bytes from the local CAS or from a provider, and restoring a historical version to the live path with rollback on failure. It also decides whether a file or one of its versions may leave the machine through the MCP surface, after it has refreshed the rule set (`remote_read_allowed`, `remote_version_allowed`).

## Dependencies

- `store::Store` and `PendingVersion` (ledger persistence), `archive::CasStore` and `assert_under_workspace` (content store and path containment), `crypto::{digest,load_archive_key,seal,open}` (SHA-256, AES-GCM archive envelope), `diff::changed_sections` (section-level change detection), `policy::{LadonPolicy,PendingPolicy,RuleStamp,walk_entry}` (ignore rules, the rule-set stamp, the background rule scan and walk error conversion), `provider::StorageProvider` (external archive transport), `model` records (`FileRecord` and `VersionRecord` for the remote gates).
- `walkdir` for scans, `chrono` for archive verification timestamps, `uuid` for temporary and backup file names, `sha2` and `hex` for `digest_file`, `anyhow` for errors, `tokio` for the async runtime that callers provide.
- `config/examples/.LADONignore` embedded with `include_str!` as the default rule file. The optional environment variable `LADON_GLOBAL_IGNORE` adds a global rule file to the policy; when the variable is set and names a file that cannot be read, loading the rules fails.
- Callers: the `ladon` CLI commands in `src/entry.rs` (`tag-folder` and `resolve_record` among them); `agent_api::AgentApi::allow_remote_read`, which calls `content_is_excluded`; `doctask_service::EngineGate`, which implements the transfer gate with `refresh_policy_if_stale`, `remote_read_allowed` and `remote_version_allowed`, and is used by `doctask_mcp`, which also calls `Engine::open`; the Slint GUI crate in `ui-prototype` (`Engine::open`, `Engine::init`, `archive_version`, `capture`, `restore`, `load_version`, `reload_policy`); integration tests.

## Public Contract

- `Engine::init(path)` canonicalises the root, creates `.ladon`, initialises the database and writes the default `.LADONignore` when absent. It checks the global and root rule files with `LadonPolicy::check_root` and starts the full rule scan with `PendingPolicy::start`, without waiting for the scan. `Engine::open(path)` requires an existing `.ladon/meta.turso` and fails with the error ``workspace not initialized; run `ladon init` `` otherwise. It checks the global and root rule files the same way, so it fails with `root rule file .LADONignore is missing` when the root holds no `.LADONignore` in any ASCII case, and it starts the scan without waiting. When `LADON_GLOBAL_IGNORE` is set and names a file that cannot be read, or the root rule file does not parse, `init` and `open` return that error.
- `reload_policy()` checks the global and root rule files synchronously with `LadonPolicy::check_root`. On failure it marks the policy invalid, which blocks every archive transfer until a later reload succeeds, and returns the error. When the root `.LADONignore` is missing, the rule set in force is replaced by a failed one, so captures are refused as well, with the message of the failed check; otherwise the rule set that was current before the call stays in place for captures. On success it starts a new full rule scan that replaces the current one and returns without waiting. The rule files below the root are read only by that scan. Captures and archive transfers wait for the scan that is current; a scan that failed returns its error to them, so the operation fails and nothing is recorded or transferred. `reload_policy` records no stamp and does not reset the interval of `refresh_policy_if_stale`. A background traversal that `refresh_policy_if_stale` started and that has not finished is not discarded by it: a later refresh call that finds the stamp unchanged and the policy valid installs that traversal when it finishes, in place of the rule set that `reload_policy` started.
- `resolve(path)` accepts absolute or workspace-relative paths. It fails with an I/O error when the path does not exist; with `symlink capture forbidden` when the path itself is a symbolic link; with `path escapes the workspace` when the canonical path is outside the root; with `symlink/nonfile capture forbidden` when the canonical path is a symbolic link or is not a regular file, such as a directory or the `.git` directory; and with `internal file cannot be tracked` when a regular file has a `.ladon` or `.git` component. It returns the canonical path and the forward-slash relative path.
- `relative_for_input(path) -> Result<String>` returns the forward-slash ledger path for a caller-supplied path. A relative path goes through `resolve`, and its errors are those of `resolve`. An absolute path that starts with the root as written is returned relative to the root without a file-system check. Any other absolute path, such as a plain Windows path that the verbatim prefix of the canonical root does not match, is resolved through its parent directory: the parent is canonicalised and the file name is joined back, so the file itself need not exist and a tracked file that was deleted is found. The containment and internal-path checks of `resolve` (`path escapes the workspace`, `internal file cannot be tracked`) apply to the result; the file type is not checked, and a missing parent directory fails with its I/O error. `resolve_record` in `src/entry.rs` calls it for absolute input.
- `normalise_relative(input) -> String` (free function, not a method): replaces each backslash with `/`, drops empty and `.` components, and joins the rest with `/`. `..` components are kept, and no file-system check is made. `resolve_record` in `src/entry.rs` uses it for a relative caller path; an absolute caller path goes to `relative_for_input`.
- `capture(path, actor, reason) -> Result<CaptureResult>`: stores the file in the CAS and hashes it. When the hash equals the hash of a record that is not marked deleted, the result has status `unchanged` and no version. Otherwise it appends a version with `changed_sections`: `DIFF_DEFERRED_PREVIOUS_COLD` when the previous content is not in the local CAS, `LARGE_BINARY_OR_TEXT` for files above 8 MiB, an empty list when bytes are identical to the previous content, else the structured diff. `sensitive` reflects the policy decision at capture time, also for unchanged files. Capture waits for the current rule scan before it hashes the file; when that scan failed, capture returns the scan error and records nothing.
- `scan(actor)` captures every regular file under the root except entries named `.ladon` or `.git` at any depth (skipped with their contents) and the root-level `.LADONignore`; a `.LADONignore` in a subdirectory is captured and flagged sensitive. Before each file it checks the rule set: when the rule set did not load, the scan stops at once with that error. A file whose capture fails does not stop the scan: the remaining files are still captured and the deletion pass still runs, and the scan then fails with one error, `scan could not capture <n> file(s): <path> (<cause>); ...`, that names every failed file. A file whose capture failed is not marked deleted. The deletion pass marks ledger entries whose files are no longer present as deleted (reason `missing during full scan`). A directory walk error stops the scan with `failed to scan the workspace: <cause>`; captures made before the error remain recorded and no deletion is recorded.
- `file_by_path(path)` normalises backslashes and returns the ledger record or the error `file not found in ledger`.
- `content_is_excluded(hash) -> Result<bool>`: true when `Store::is_hash_sensitive` reports that a version with this content hash is flagged sensitive, or when any tracked path that holds a version with the hash, live or marked deleted (`Store::paths_for_hash`), is excluded by the current rules; each such path is joined to the root one component at a time (`workspace_path`) before the rule check. It does not read the sensitive flag of one version; `archive_version` checks that flag itself. It waits for the current rule scan, and a failed scan returns its error. `archive_version` and `AgentApi::allow_remote_read` call it. When an endpoint and a model are given, the CLI `tag-folder` command in `src/entry.rs` calls it with the ledger hash of each tracked file whose path `LadonPolicy::excluded` does not exclude; the remote AI call is skipped when either check is true, unless `tagging::local_endpoint` accepts the endpoint. Known limitation: `tag-folder` judges a file by its ledger hash, so a tracked file overwritten with excluded bytes but not yet captured is judged by its old hash, while the bytes it sends are read from disk.
- `archive_version(version_id, provider, evict_local) -> Result<StorageObject>`: refuses when the policy is invalid (`policy reload failed: all external archive transfers blocked`), when the policy forbids external transfer for the path (`LADON policy denies external data transfer`), or when the version is sensitive or `content_is_excluded` returns true for its content hash (`sensitive version blocked from external storage`). Stored flags are not trusted alone: every holder path is evaluated against the current rules, so a path that a rule covers blocks the archive. It requires `LADON_ARCHIVE_KEY_HEX` (64 hex digits; errors name the missing variable, `64 hex digits` or `exactly 32 bytes`). If the ledger already holds an archive record for the content hash with the same provider name, it fetches that object from the provider (a missing remote object returns the provider error), authenticates it, optionally evicts the local copy, and returns the stored record without writing a new one. Otherwise it seals the local bytes, uploads, reads back and authenticates the object, records it, and optionally evicts the local copy. The local copy is evicted only after the remote object authenticated; an object that fails authentication yields `archive authentication failed` and keeps the local copy. A first archive needs the local copy (`local copy unavailable for first archive`). The exclusion check waits for the current rule scan, and a failed scan returns its error before any key is read or any object is uploaded. Known limitation: `LadonPolicy::excluded` does not normalise `..` components, so a path that contains a `..` component is not rejected by its outside-workspace check, whether the path is relative or an absolute path under the root.
- `load_version(version_id, provider)`: returns bytes from the local CAS when present; otherwise needs a provider that holds an archive record for the content hash, downloads, decrypts and verifies the hash. Errors: `unknown version`, `historical content is cold; supply matching provider`, `no archived location found`. Local bytes are read up to 128 MiB (`MAX_ARCHIVE_IN_MEMORY`); a larger local object fails with `object exceeds bounded read limit`.
- `restore_plan(version_id) -> Result<String>` returns a multi-line description beginning `RESTORE PLAN: {file id} version {number} ({content hash}) -> {relative path}` followed by `Target exists: true|false` and the approval requirement. It reads the ledger and checks whether the target exists, and changes nothing.
- `restore(version_id, approve, provider)`: requires `approve` (`restore requires explicit --approve`) and refuses when a live file exists at the target and its hash differs from the ledger (`live file changed outside ledger; scan before restore`). The historical bytes are loaded with `load_version` before the live file is touched. They are written to a temporary file in `.ladon/restore`, named from the target's file stem with `.ladon-restore-<uuid>`. An existing live file is moved aside to a backup in `.ladon/restore`, named from the target's file stem with `.ladon-backup-<uuid>`. The backup is hashed again: when its hash differs from the ledger or it cannot be read, it is moved back to the live path, the temporary file is removed, nothing is recorded and the call fails with the same `live file changed outside ledger; scan before restore` message. When the backup cannot be moved back, the error names the backup path (`live file changed during restore and could not be put back; its bytes are at <backup>`). `restore` calls `restore_with_hook`, which takes four hooks (`before_backup`, `before_place`, `before_capture`, `before_rollback_removal`) that let tests stand in for a concurrent writer or a failed capture; `restore` passes no-op hooks.
- Restore placement: the temporary file is placed at the target without replacing anything, by a hard link where the volume supports one (a volume that reports hard links as unsupported gets the copy), and otherwise by a copy created with `create_new`. When a file already exists at the target, the call fails with `a file appeared at <target> during restore and was left as it is`, followed by the backup path when a pre-restore file existed; the backup is kept. Any other placement failure puts the backup back at the target by the same no-replace placement when that succeeds, and then removes the backup. The temporary file is removed after the placement attempt, and nothing is recorded.
- The placed file is captured through `capture` as actor `restore` (a new version with event kind `restored` and status `captured` when the record is marked deleted, a new version with event kind `modified` otherwise when the content differs from the record, and status `unchanged` with no new version when the restored bytes equal the hash of a record that is not marked deleted). When the capture succeeds, the backup is removed; when that removal fails, the restore still returns the captured result, and the backup stays in `.ladon/restore` with no error reported.
- When the capture fails, the target is moved aside to a `.ladon-discard-<uuid>` file in `.ladon/restore`, and the moved-aside file is hashed. When it holds the restored bytes, it is removed, the pre-restore file is moved back from the backup (when one existed), and the capture error is returned. When it does not hold them, or the target could not be moved aside, the moved-aside file is moved back to the target when it was moved aside, and the call fails with `restore capture failed (<cause>); the live file at <target> no longer holds the restored bytes and was left as it is`, followed by `; the pre-restore bytes are at <backup>` when a pre-restore file existed. When the aside file cannot be moved back, the call fails with `live file changed during rollback and could not be put back; its bytes are at <aside>` in place of the capture error. When a pre-restore file existed and a file is written to the target during the rollback, that file is kept, the backup is not moved over it, and the call fails with `restore capture failed (<cause>); an edit was written to <target> during rollback and was left as it is`, followed by the backup path. When no pre-restore file existed, a file written to the target during the rollback is kept and the call returns the capture error unchanged.
- The digests used by the restore (the live file before the restore, the backup after the move aside, and the moved-aside target after a failed capture) are computed by `digest_file`, which reads the file in 64 KiB chunks and returns the same value as `crypto::digest`; `load_version` still loads the historical bytes whole.

- `refresh_policy_if_stale() -> Result<()>` (not async): the rule freshness check that both remote gates run before they decide. It compares the stamp of the root `.LADONignore` files (any ASCII case) and of the global file named by `LADON_GLOBAL_IGNORE` with the stamp recorded when the rule set in force was started. A file's stamp holds its modification time, its length and its SHA-256 digest, so an edit that keeps size and time is still seen. A missing file has none of the three, and each call reads every stamped file in full to compute its digest. When the stamp differs, or the policy is marked invalid, the call runs `LadonPolicy::check_root`; the invalid mark is checked on every call, so a broken file restored exactly, with an unchanged stamp, reopens the gate. A failure marks the policy invalid, installs a failed rule set when the root rule file is missing, returns the error and records no stamp, so the next call checks again. When `LadonPolicy::check_root` passes, the call loads the complete rule set on the calling thread (one traversal), installs the result whether it loaded or failed, marks the policy valid, records the stamp read at the start of the call and returns `Ok(())`; an edit made during the load changes the stamp, so the next call sees it. `Ok(())` means only that the root and global rule files passed `check_root`: a nested rule file that fails the load leaves a failed rule set in force, which both remote gates refuse. When the stamp matches and the policy is valid, the call first installs a finished background traversal, whether it loaded or failed, and then, when no background traversal is in flight and at least 30 seconds have passed since `refresh_policy_if_stale` last started a traversal or the engine was opened (the interval is the engine field `nested_interval`, set to 30 seconds by `init` and `open`), starts one with `PendingPolicy::start` and returns without waiting. The rule set in force stays in use until that traversal has finished. A call that finds the stamp changed, or the policy marked invalid, discards a background traversal in flight, because that traversal may have read an older root or global file. `init` and `open` record the stamp before their own scan starts.
- `rule_traversals() -> usize`: the number of rule-set traversals started by `refresh_policy_if_stale` since the engine was opened, counting synchronous reloads and background traversals. Traversals started by `init`, `open` and `reload_policy` are not counted. The count belongs to the engine, so tests in one process do not share it.
- `remote_read_allowed(file: &FileRecord) -> Result<bool>` (async): the file-level gate for data that leaves the machine through the MCP surface. It calls `refresh_policy_if_stale` first and returns `Ok(false)` when that refresh fails, when the policy is invalid or its load failed (including a global rule file that cannot be read), when `file.sensitive` is set, when `LadonPolicy::allow_external` refuses `file.relative_path` (the rule set excludes it), or when `content_is_excluded(file.current_hash)` is true. Otherwise it returns `Ok(true)`. Callers treat an `Err` (store failure, poisoned lock) as a refusal.
- `remote_version_allowed(version: &VersionRecord) -> Result<bool>` (async): the version-level gate. It refreshes the rules and returns `Ok(false)` when that refresh fails, when the policy is invalid or its load failed, when `version.sensitive` is set, or when `content_is_excluded(version.content_hash)` is true. Otherwise it returns `Ok(true)`. It does not look at the current path of the file: a historical version is judged by its own flag and by the tracked paths that hold a version with its bytes, so a file that is allowed now does not make its older versions allowed.
- `remote_path_allowed(relative: &Path) -> Result<bool>` (async): the path-level gate for a path that may be untracked. It returns `Ok(false)` when `rules_usable` is false (the rules in force cannot be refreshed, or the policy is invalid or failed to load), and when `LadonPolicy::allow_external` refuses `relative` on the rule set in force; a path outside the workspace is refused by that check. When `relative` maps to a tracked file (through `relative_for_input`, or as written when the mapping fails), the decision is `remote_read_allowed` on that file record, so a flagged file, a tracked copy of excluded content and a directory alias are refused. An untracked path that the rules allow returns `Ok(true)`. Callers treat an `Err` as a refusal. It is used by `AgentApi::allow_remote_read` and by the `ignore-check` command.
- Readiness of the rule set in force (`PendingPolicy` in `src/policy.rs`): `PendingPolicy::start` loads the full rule set (global file, root rule files and nested rule files) on one background thread named `ladon-rule-scan` and returns at once; if the thread cannot be started, the rule set is stored as failed with `rule scan could not start`. `is_ready` reports whether the load has finished, successfully or not, and a poisoned lock counts as finished. `with` waits until the load has finished and then runs its closure on the rule set; a failed load returns its stored message on every call. `PendingPolicy::ready(result)` and `PendingPolicy::failed(message)` create a finished rule set. `capture`, `scan` (through `rules_ready`), `content_is_excluded`, `archive_version`, `rules_usable` and `remote_read_allowed` reach the rule set in force through `with`, so each waits for it. A failed rule set makes `capture`, `scan`, `content_is_excluded` and `archive_version` return the stored error, and makes both remote gates return `Ok(false)`.

## Change Notes

- The remote gates are async because `content_is_excluded` reads the ledger. Both gates refresh the rules before they decide and map every refusal, including an invalid rule set, to `Ok(false)`.
- A nested `.LADONignore` edit reaches the gates after the 30-second interval has passed and one background traversal has finished, so the window is 30 seconds plus one traversal. Root and global rule-file edits reach the next gate call.
- A gate call waits for the rule set in force to finish loading, as `capture` does, so the first gate call after `open` waits for the traversal that `open` started.
- `capture` and `archive_version` do not refresh the rules. The result of a background traversal reaches them with the next call of a remote gate.
- Global and root rule-file errors are returned by `Engine::init` and `Engine::open`; nested `.LADONignore` errors surface through `capture`, `archive_version` and `scan`, and `scan` stops with them before the next file it would capture.
- `capture` and `archive_version` wait for the current rule scan, and `scan` waits before each file it captures. When the rule set failed, `capture` and `archive_version` return its error before any record is written, and `scan` returns it before the next file it would capture; `archive_version` returns it before the archive key is loaded and before any object is uploaded.
- `restore_plan` checks the target with `self.root.join(&file.relative_path)` and changes nothing.
- `archive_version` evicts the local copy only after the remote object authenticates.
- Known limitation: `scan` skips the root `.LADONignore`, so a ledger entry for that file, created by an explicit capture, is marked deleted by the first full scan after it is tracked, and later scans skip it.
- Known limitation: `ledger_path` tests the whole canonical path for `.ladon` and `.git` components, so a workspace located under a folder with either name refuses every capture with `internal file cannot be tracked`.
- Known limitation: `normalise_relative` keeps `..` components and does not change letter case, and `Store::find_path` matches the stored path exactly, so `DOCS\A.md` and `docs\..\docs\a.md` are not found in the ledger.
- Known limitation: `relative_for_input` fails with the I/O error of `canonicalize` when the parent directory of an absolute path no longer exists.
- Known limitation: every `capture` reads and compresses the whole file before it compares hashes, and an object removed by `archive --evict-local` is written back by the next capture of the unchanged file.
- Known limitation: when fetching or authenticating an existing archive record for the provider fails, `archive_version` returns that error, uploads nothing and leaves the record unchanged, so a damaged remote object is not repaired by the command.
- Known limitation: the restore calls that move a file back to the target in `restore_with_hook` (the put-back after a failed backup digest check, the rollback move back of the aside file and the rollback move back of the backup) use `fs::rename`, which replaces an existing file at the destination. The rollback move back of the backup ignores its error, so a failed capture whose backup cannot be moved back returns the capture error without the backup path.
- Known limitation: when the target cannot be moved aside during the rollback of a failed capture, the error still says that the live file no longer holds the restored bytes, although the target was not moved and may still hold them; the pre-restore bytes are at the backup path when one existed.
- Known limitation: a temporary file stays in `.ladon/restore` when writing it or moving the live file aside fails.
